## Problem Statement
A referral is written, and then nothing happens. An estimated 30–50% of outpatient specialty referrals are not completed (Int J Med Inform 2023, S1386505623002836). These figures come from US specialty-care settings and are illustrative for a CHW setting until a locale-specific source is added. In a study of 103,737 referral scheduling attempts, only 34.8% ended in a documented visit (PMC5910374). The gap between "referred" and "seen" has no owner. The patient hits a barrier, nobody learns which one, and the CHW never finds out whether the patient arrived (PMC6489304).

The product is a low-bandwidth SMS (and optionally voice) agent. It contacts each referred patient, works out **why** the referral is stuck, takes the **smallest permitted administrative action**, escalates to a human when needed, and **confirms the visit happened**. It never diagnoses or gives clinical advice.

## What Makes This Cool
- **It acts. It doesn't just inform.** At least one action goes to the *clinic*: "Patient R-0142 arriving Thu 9am, reply Y if seen." The agent coordinates people instead of answering questions.
- **CHW relay baton.** On escalation the CHW gets one SMS with the barrier, what was already tried, and the patient's own words. Reply `1` to take the case. If nobody claims it in N minutes, it goes to the next CHW.
- **Clinic Reliability Radar (the punchline).** Patient-reported barriers are added up per clinic. The finding is "Clinic B: 6 of 11 patients this week found it closed or were turned away." That gives a per-facility reliability *signal* (to be confirmed, since it rests on patient reports) from data the system already logs. The demo ends on "we found the broken clinic," not on another chatbot.

## Constraints
- 24–48h build, live demo in front of judges.
- Low bandwidth: plain SMS (GSM-7, ≤160 chars where possible), no app, works on a feature phone.
- Safety: no diagnosis, no free-form medical advice, every clinical mention escalates.
- Synthetic data only. No real PHI in the demo.

## Premises (agreed)
1. One live SMS path end to end over Twilio. Everything else is seeded. Voice is a stretch goal: one scripted outbound `<Say>` + `<Gather>` call.
2. **The LLM classifies. Code decides.** The model returns `{barrier, confidence, fields}` from a fixed enum that includes `unknown`. A deterministic router and rules table pick the action; clinical signals always take precedence. Patient-facing text is approved templates with slots, never model free text.
3. At least one action faces the clinic (notify clinic, ask clinic to confirm attendance), because the evidence says failures are mostly system-side (appointment access, hours, finding the office; PMC3752985).
4. `completed` requires a patient "yes" **or** a clinic/CHW confirmation. Clinic confirmation is the stronger signal and is shown as such.
5. A ~100-message labeled eval with a confusion matrix is part of the demo. Misclassifications should land in `unknown → escalate`, not in a wrong action.

## Recommended Approach (C)

### Architecture
```
Referral (seed / form) ─► cases table
        │
        ▼
Twilio SMS ──► /sms webhook ─► ROUTER (deterministic, no LLM)
                                 │  0. patient inbound → clinical keyword pre-filter FIRST (always)
                                 │  1. STOP/START/HELP keywords → opt-out handling
                                 │  2. sender phone ∈ chws  → CHW command parser ("1 R-0142")
                                 │  3. sender phone ∈ clinics → clinic reply parser ("Y R-0142")
                                 │  4. patient with open prompt AND message is exactly the expected token → parse locally
                                 │  5. otherwise (patient free text) ↓
                                 ▼
                     clinical keyword pre-filter ─(hit)─► clinical_symptom path
                                 │ (no hit)
                                 ▼
                     classify(msg) → {barrier, confidence, clinical_flag, fields}
                                 │  LLM, JSON-only, 3s timeout
                                 ▼
                     validate(fields) ─► rules.decide(case, result)   ← deterministic
                                 │
        ┌───────────────┬────────┴───────┬──────────────────┐
        ▼               ▼                ▼                  ▼
 patient template   clinic SMS      CHW baton SMS     schedule follow-up
        └──────────► events log (every barrier + action, with facility_id) ◄───┘
                                 │
                                 ▼
          dashboard (polls /api/state every 2s): metrics + clinic radar
```
One process (FastAPI or Express), one SQLite file, and a scheduler tick every 15s that fires anything with `due_at <= now() + clock_offset`. Twilio for SMS (+ optional voice).

### Inbound routing (fixes reply correlation)
- The **role comes from the sender's phone number**: `chws.phone`, `facilities.phone` or `cases.patient_phone`.
- **CHW and clinic replies include the case ID.** Every outbound prompt to them ends with "Reply 1 R-0142" or "Reply Y R-0142 / N R-0142". The parser accepts `1 R0142`, `1 0142` or `y 142` (case-insensitive, prefix optional). A bare `1`/`Y` maps to the **most recent open prompt** to that number, and only if exactly one is open. Otherwise the agent replies "Which case? Reply 1 R-xxxx".
- **The clinical pre-filter runs on every patient inbound before anything else.** A hit goes to the clinical path even if the message also answers an open YES/NO prompt.
- **Patient control replies** are parsed locally only when the trimmed, case-folded message is *exactly* an expected token (`yes`/`y`/`no`/`n`/`2`, plus local-language equivalents) for an open `prompts` row. Anything longer ("no, the clinic was shut") goes to the classifier.
- `STOP` (Twilio-enforced): set `cases.opted_out=1`, cancel all pending patient-bound prompts and reminders, log an `opt_out` event, and hand the case to the CHW baton ("Patient opted out of SMS, call if appropriate"). If no CHW claims it within 7 days the case is `lost`. `START` clears the opt-out.

### Classifier contract
Output: `{barrier, confidence, clinical_flag: bool, fields}`.
Barrier enum: `transport · cost · wrong_facility · missing_documents · scheduling · clinic_closed · turned_away · language · fear_confusion · clinical_symptom · plan_ack · unknown`.
`plan_ack` = no barrier reported: acknowledgements and stated plans ("ok thanks", "ok i can go monday"). It never opens a baton.
`no_response` is a **timer state**, not a classification.

Decision order, all in code:
1. **Clinical precedence.** If the keyword pre-filter hits (see *Clinical pre-filter* below), **or** `clinical_flag=true`, **or** `barrier=clinical_symptom` at *any* confidence, the clinical path runs. This happens even when the message also names an administrative barrier. That barrier is logged too, but its action waits until the clinical baton is claimed.
2. If the API errors or times out (3s), or the output fails JSON/enum validation, the result is `unknown` and goes to a non-clinical baton.
3. If `confidence < τ` (start at 0.7, tuned on the eval) or the message names more than one administrative barrier, the result is `unknown`.
4. Otherwise the barrier's rule runs.

**Clinical pre-filter** (`clinical_terms.txt`): case-insensitive, word-boundary, single-term match against listed variants. If *any* term matches, it's a hit; no combinations needed. Seed list: pain, painful, hurt, hurts, hurting, ache, aching, bleed, bleeding, blood, fever, hot body, vomit, vomiting, diarrhea, can't breathe, cant breathe, breathing, chest, faint, fainted, dizzy, seizure, swollen, swelling, worse, emergency, plus slang and local-language variants for the chosen locale. False positives are acceptable: they only escalate.

Allowed `fields`, validated by code before use. A field that fails validation is dropped. If the rule needed it, the case falls back to the CHW baton, and the field is never inserted into a message.
| field | type / validation | used by |
|---|---|---|
| `return_date` | parsed to a date, today ≤ d ≤ today+30 | clinic_closed, turned_away, scheduling, plan_ack |
| `language` | ∈ supported template languages | language |
| `area` | ∈ known `areas` list (exact or fuzzy match ≥ 0.9) | wrong_facility |
| `missing_doc` | ∈ facility `required_docs` | missing_documents |

### Rules table (barrier → permitted action)
| Barrier | Patient action (template) | System action |
|---|---|---|
| transport | directions + transport instructions from facility DB | — |
| cost | "Service is free / bring X" from facility DB, if `cost_note` exists | if no `cost_note` → CHW |
| wrong_facility | reroute to a facility in the patient's `area` that offers `service` (or the first match in the district) | log the event against the **original** facility; re-point the case; notify the new clinic |
| missing_documents | checklist from facility `required_docs` | — |
| scheduling | static appointment instructions (how to book, hours, phone) | if `return_date` is valid → set `visit_date`, notify clinic "patient arriving <date>" |
| clinic_closed | the facility's posted hours, or an alternative facility if it's closed for > 3 days | **radar event**; if `return_date` is valid → set `visit_date` + notify clinic |
| turned_away | "We've told the clinic you're coming on <date>" (if `return_date` is valid), else CHW | **radar event**; notify clinic |
| language | resend in the patient's language (pre-translated templates) | if unsupported → CHW |
| fear_confusion | plain-language explanation template | offer CHW call ("reply 2 to talk to someone") |
| clinical_symptom | "A health worker will contact you now. If it is severe, go to <emergency facility> or call <emergency number>." | **clinical baton** |
| plan_ack | "Thanks! See you at <clinic> on <date>." (or a plain "Thanks!" with no date) | if `return_date` is valid → set `visit_date`, notify clinic "patient arriving <date>"; **no baton** |
| unknown | "Thanks, a health worker will follow up." | non-clinical baton |

There is no "next open slot". The facility DB has no slot data, so scheduling sends static instructions.

### CHW baton
- Offer the case to active CHWs in order (round robin starting with the CHW assigned to the case's area). Each offer is a `prompts` row with `expires_at`.
- **Timeouts:** clinical 5 min per CHW; non-clinical 60 min per CHW (demo: 2 min / 5 min).
- **When every CHW times out or none is active:** clinical cases → SMS the `supervisor_phone` (config) and re-send the emergency-instructions template to the patient. Non-clinical cases → supervisor SMS, then go round the list again once. Every offer, timeout and exhaustion is an event.
- A claim sets `cases.claimed_by_chw`. The CHW closes their part with `DONE R-0142` (the case resumes the referral flow at `action_taken`) or `LOST R-0142`.

### Case state machine
Main path: `referred → contacted → barrier_found → action_taken → visit_scheduled → follow_up → completed | lost`.
`escalated` is a **flag** (`cases.escalation = none|clinical|non_clinical`) that can attach to any non-terminal state. While it's set, automated patient messaging pauses except for safety templates. CHW `DONE` clears it and moves the case to `action_taken`. A clinical case *does* continue the referral flow after `DONE`, because the referral is still owed.

No response: no reply 48h after an outbound prompt → reminder (`reminder_count++`). After 2 reminders → non-clinical baton.

**Lost:** no inbound from the patient **and** no CHW claim for 7 days, counted from the **last outbound message**. Or a CHW sends `LOST`.

### Follow-up and completion rules
On `visit_date + 1 day` (or the fast-forward button) the agent asks both parties: patient "Did you get seen at <clinic>? Reply YES / NO", clinic "Was R-0142 seen? Reply Y R-0142 / N R-0142".
| Patient | Clinic | Result |
|---|---|---|
| any / none | **Y** | `completed`, `completed_by=clinic` (clinic wins) |
| YES | none after 48h | `completed`, `completed_by=patient` (shown as weaker) |
| YES | **N** | conflict → non-clinical baton, the CHW resolves it, `completed_by=chw` or back to `action_taken` |
| NO | none / N | back to `barrier_found`: ask "What got in the way?" and run the classifier again |
| none | none after 48h | non-clinical baton |

### Data model (SQLite)
- `facilities(id, name, services[], area, address, hours_json, phone, required_docs[], cost_note, language)`
- `areas(name, district)`: small fixed list
- `cases(id 'R-0142', patient_phone, patient_lang, patient_area, service, facility_id, referred_at, visit_date, status, escalation, latest_barrier, reminder_count, claimed_by_chw, opted_out, completed_by)`
- `prompts(id, case_id, to_phone, role, expects 'yes_no'|'claim'|'seen'|'free_text', sent_at, expires_at, resolved_at)`: pending-prompt state, used for routing and timers
- `events(id, case_id, ts, actor 'patient'|'agent'|'clinic'|'chw'|'system', kind, barrier, facility_id, payload_json)`: append-only. **`facility_id` is the facility at the time of the event.**
- `chws(id, phone, name, area, active)` · config: `supervisor_phone`, `emergency_number`, `clock_offset`

`cases.latest_barrier` is for display only. **All barrier analytics come from `events` where kind='barrier'.**

### Dashboard (single page, polls every 2s)
- Referral completion rate (split clinic-confirmed / patient-reported) · unresolved count · median time to completion
- Top barriers (count of distinct cases reporting each barrier, from events) · % resolved without a CHW vs escalated
- **Clinic Reliability Radar:** for each facility, the **share of distinct cases that reported `clinic_closed` or `turned_away` at that facility** (attributed through `events.facility_id`), shown as "6 of 11 patients". `wrong_facility` and `scheduling` are excluded because they usually aren't the clinic's fault. Facilities with n < 5 are greyed out. The label is "**signal: needs follow-up**", not a score, because it rests on patient self-report.
- Case timeline view for the demo patient.

### Demo script (≈3 min)
Tell the judges up front that the 40 background cases are **synthetic seed data**. The live case is the only real input.
1. The dashboard shows the seeded cases across 4 clinics. Clinic B's radar signal is elevated.
2. Create referral R-0142 for the demo phone (a pre-verified handset, or a judge's phone if it's verified). The phone gets an SMS within seconds.
3. Reply **"went there yesterday the gate was locked, nobody there"**. The gold label is `clinic_closed`, and this phrasing and its variants are in the eval. The patient gets Clinic B's posted hours. Then reply **"ok i can go monday"**. That is `plan_ack` with `return_date`=Mon (in the eval with this gold label and action), which sets `visit_date` and sends the clinic "R-0142 arriving Mon." Clinic B's radar ticks up on the next poll.
4. Reply **"also my stomach still really hurting"**. The pre-filter matches "hurting", so this is `clinical_symptom`. The patient gets the safe escalation template and the CHW phone (a teammate) gets "CLINICAL R-0142 … Reply 1 R-0142". The teammate claims it, then sends `DONE R-0142`.
5. Press fast-forward (adds `clock_offset` so the follow-up is due). The clinic phone replies `Y R-0142` → `completed (clinic-confirmed)`. The completion rate moves.
6. Close on the eval: the confusion matrix, **0 clinical messages missed**, and the measured wrong-action rate (see Success Criteria). Claim only what was measured.

### Eval design
- 150 messages: 10 per administrative barrier, 10 `plan_ack` (including "ok i can go monday" + variants), **30 clinical** (direct, indirect, slang, mixed with an administrative barrier, **clinical text inside YES/NO replies**, and "also my stomach still really hurting" + variants), and 20 multi-barrier or ambiguous messages with gold label `unknown`.
- **Held-out split:** a teammate who doesn't tune the prompt writes 50 of them. Report numbers on the held-out set.
- Scoring:
  - (a) **Barrier accuracy**: `unknown` on a single-barrier message counts as *safe but wrong*. Report it separately and don't count it as correct.
  - (b) **Wrong-action rate**: the share of messages whose *action* differs from the gold action and isn't an escalation. This is the number the closing claim rests on.
  - (c) **Clinical recall** (pre-filter + classifier combined).
  - (d) Error rates above and below τ, to check the confidence gate. If errors above τ are still high, switch to agreement across 3 samples.

## Reviewer Concerns

Disposition: CONCERNS_RECORDED

Stop: CONVERGENCE

### R2-1 — completeness

**Problem**

> Safety gap in the router: step 4 parses patient YES/NO/2 replies locally when a prompt is open, and the clinical keyword pre-filter only runs at step 5. A reply such as 'NO, my chest hurts and I fainted' to the follow-up question would be consumed as a NO (back to barrier_found) or a YES, and the clinical path would never run. This breaks 'every clinical mention escalates' and Premise 2's 'clinical signals always take precedence'.

**Remedy**

> Run the clinical pre-filter on every patient inbound before any local parse, or restrict local parsing to messages that are exactly the expected token (after trimming/case-folding) and send everything else through the pre-filter and classifier. Add YES/NO replies with clinical content to the clinical eval.

### R2-2 — consistency

**Problem**

> In the architecture, a pre-filter hit goes straight to the clinical_symptom path and skips classify(). Decision-order rule 1 says that when a clinical message also names an administrative barrier, 'that barrier is logged too, but its action waits'. On the pre-filter path no classifier runs, so no administrative barrier can be identified, logged or acted on later.

**Remedy**

> Either still run the classifier after a pre-filter hit (to log the administrative barrier only, never to downgrade the clinical routing), or state that on a pre-filter hit the administrative barrier is left for the CHW to record.

### R2-3 — consistency

**Problem**

> The deferred administrative action for a mixed clinical message waits 'until the clinical baton is claimed' (decision order rule 1). The escalation flag section says automated patient messaging pauses while the flag is set, and only CHW `DONE` clears it. Claim and DONE are different moments, so it is unclear whether the deferred action fires on claim or on DONE, and whether it then breaks the messaging pause.

**Remedy**

> Choose one trigger, either claim or DONE, for releasing deferred administrative actions, and make it agree with the escalation-flag pause rule.

### R2-4 — completeness

**Problem**

> When the pre-filter misses (e.g. a new slang term) and the classifier then times out or fails validation, rule 2 sends the message to a *non-clinical* baton (60 min per CHW) with the generic 'Thanks, a health worker will follow up' template. During an LLM outage, any clinical message the keyword list misses gets the slow, non-emergency path.

**Remedy**

> Decide explicitly. Either route classifier failures to the clinical baton timing with the safety template, or accept the risk and state it. Then include outage behavior in the clinical-recall reasoning.

### R2-5 — completeness

**Problem**

> The barrier enum has no label for free-text patient messages that report no barrier: acknowledgements, thanks, or stated plans ('ok thanks', 'i will go tomorrow'). By the decision order these become `unknown` and fire a CHW baton, which will flood CHWs. Demo step 3's second message, 'ok i can go monday', is a stated plan, not a scheduling barrier. The demo depends on the classifier labelling it `scheduling` with a return_date, and the eval does not cover this phrasing.

**Remedy**

> Add a non-barrier label (e.g. `ack`/`plan`) and its rule (no baton; set visit_date if a valid return_date is present), or document that such messages map to scheduling. Add 'ok i can go monday' and its variants to the eval with a decided gold label and gold action.

### R2-6 — completeness

**Problem**

> The role comes from the sender's phone, but the document never says which case a patient message belongs to when one patient_phone has several open cases. Shared family feature phones are common in the target setting. Case IDs are required only from CHWs and clinics, not from patients.

**Remedy**

> Define how a case is chosen for patient phones with more than one open case: most recent prompt, most recently referred, or a disambiguation SMS. Alternatively, enforce at most one open case per phone in the seed data and the referral form.

### R2-7 — completeness

**Problem**

> The follow-up resolution table has no row for patient none + clinic N. The 'NO | none / N' row needs a patient NO, and the 'none | none' row needs the clinic to be silent too.

**Remedy**

> Add the patient none / clinic N row. A likely choice is to ask the patient 'What got in the way?' and then send the case to the non-clinical baton if there is still no reply.

### R2-8 — clarity

**Problem**

> The follow-up table reads as if both answers are known at once, but replies arrive one at a time. A patient NO immediately triggers 'back to barrier_found' and a new classifier run. If the clinic later replies Y ('clinic wins'), the case may already be inside a new barrier/action cycle. The same applies to a patient YES that arrives before a clinic N.

**Remedy**

> State whether outcomes are applied as each reply arrives (and how a later clinic reply overrides an earlier transition) or only when the 48h window closes, and what happens to in-flight barrier actions when the clinic later confirms.

### R2-9 — completeness

**Problem**

> The baton still has no final end state after its fallback. For clinical cases, nothing says what happens after the supervisor SMS and the resent emergency template: whether CHWs are re-offered the case and whether the supervisor gets repeat pages. For non-clinical cases, after 'go round the list again once' the behavior when the second round also times out is undefined. The case could also drift into `lost` unnoticed.

**Remedy**

> Define the terminal behavior after the fallback for both baton types, e.g. a clinical case keeps paging the supervisor every X minutes until a claim, and a non-clinical case is marked `unclaimed` and shown on the dashboard after the second round. Log each step as an event.

### R2-10 — completeness

**Problem**

> A case that a CHW claims but never closes with DONE or LOST has no timeout. The `lost` rule needs 'no CHW claim for 7 days', so a claimed case is excluded from it. The escalation flag stays set, automated patient messaging stays paused, and the case can sit forever.

**Remedy**

> Add a claimed-case timeout, e.g. remind the CHW after N hours, re-offer or notify the supervisor after M hours, and count the case toward lost after 7 days without DONE.

### R2-11 — clarity

**Problem**

> CHW `DONE` always moves the case to `action_taken`. In the demo, visit_date has already been set (visit_scheduled) before the clinical escalation, so DONE moves the case backwards. The state machine does not say whether the visit_date+1 follow-up still fires from `action_taken`.

**Remedy**

> Have DONE return the case to its pre-escalation state (or to visit_scheduled when visit_date is set), or state that follow-up scheduling is keyed only on visit_date whatever the status.

### R2-12 — consistency

**Problem**

> The success criteria require '100% clinical recall (30/30)' on the held-out eval. The held-out split is only the 50 messages the teammate writes, and the 30 clinical messages are spread across all 150. 30/30 on the held-out set is only possible if every clinical message is in the held-out 50, and the document does not say so.

**Remedy**

> Specify how the held-out 50 are composed (e.g. at least N clinical, including indirect and mixed). Either restate the criterion as recall on the held-out clinical subset or define how many clinical items the teammate writes.

### R2-13 — feasibility

**Problem**

> The 'wrong-action rate ≤ 3%' is reported on a 50-message held-out set. Each error moves the rate by 2 points, so the criterion really means 'at most 1 wrong action'. With that sample size it says little about real-world performance, and the demo's closing claim rests on it.

**Remedy**

> Report the raw count (k/50) along with the rate, and optionally report the 100 tuning messages separately. Alternatively, enlarge the held-out set so that a 3% threshold has meaning.

### R2-14 — feasibility

**Problem**

> The clinic_closed rule sends 'an alternative facility if it's closed for > 3 days'. Nothing in the data model records unplanned closures or their length: hours_json holds posted hours only, and a patient report such as 'gate locked' gives no duration. The branch cannot be evaluated.

**Remedy**

> Either derive 'closed > 3 days' from N recent clinic_closed events at that facility, add a facility closure field set by staff or seed data, or drop the branch and always send posted hours plus the CHW option.

### R2-15 — feasibility

**Problem**

> Fast-forward adds a global `clock_offset`. Every due timer then fires at once: reminders, 48h clinic waits, baton timeouts and 7-day lost checks, on the demo case and on the 40 seeded cases. During the demo this could send stray SMS to the handsets or change seeded dashboard numbers.
